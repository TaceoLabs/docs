# What you see onchain

Each transfer mode makes a different trade between what's visible onchain, what's visible to node operators, and what's visible to no one at all.

## By mode

| | Onchain | Node operators | No one |
|---|---|---|---|
| **Confidential transfer** | Sender, recipient visible. Asset, amount encrypted | — | — |
| **Private transfer** (default) | Sender, recipient, asset, amount all encrypted | Transaction graph (which addresses transacted with which) | — |
| **Graph-private transfer** | Sender, recipient, asset, amount all encrypted | Nothing | Transaction graph |

## Why balances aren't committed individually

A naive design — one onchain commitment per account balance — leaks the transaction graph by construction: watching which commitment changed on a transfer tells you who sent to whom. Private and Graph-private transfers avoid this by storing all balances in a single oblivious hashmap (`mapping(address => balance)`), committed to onchain as one sparse Merkle root rather than one commitment per account. A transfer updates the map without revealing which entries changed.

Confidential transfer skips the oblivious hashmap: balances are committed per-address (`mapping(address => Commitment)`), which is what makes it faster and also what makes sender and recipient visible onchain.

## Why private and graph-private differ

Both use the same oblivious hashmap onchain. The difference is what the node operators running the MPC network see while executing a transfer:

- **Private transfer** intentionally reveals the wallet addresses and tree indices involved to the node operators (not onchain), letting the Merkle tree update run in plaintext at the operator layer. This is the performance trade that makes the default tier's throughput possible.
- **Graph-private transfer** keeps the access pattern oblivious to the operators too, via ORAM (oblivious RAM) at every layer of the tree — nobody, including operators, learns which addresses were involved. This costs throughput.

## Verifiability

Every mode above is backed by a coSNARK: the MPC network proves the state transition is correct (updated commitments, sender solvency) without any single party seeing the plaintext balances. This is a separate axis from what's hidden from whom — a construction that hides more from more parties isn't inherently "more verified"; verifiability is a property TACEO builds into all three modes, not a trade-off between them.
